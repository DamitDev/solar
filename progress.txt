## US-002 — Active request Redis store (DONE)

Added a per-request active registry to `RoutingStore` in
`app/redis_state/routing.py` (prefix `solar:active-req:`), the server-authoritative
source for the WebUI's active-request view:
- `create_request` — records an in-flight request on `request_start`
  (model/endpoint/client_ip/timestamp)
- `update_request` — merges routing details on `request_routed`/`request_reroute`
  (host_id/host_name/instance_id/resolved_model/attempt), returns None if the
  request is unknown
- `delete_request` — removes the entry on `request_success`/`request_error`
- `get_request` / `list_requests` — read individual or all live entries
  (used by snapshotting in later stories)

Each write issues a TTL mirroring `ACTIVE_TTL_S` (300 s, overridable per-write)
so a replica that crashes mid-request expires its entry instead of showing a
stuck 'processing' request. Cross-pod delete semantics fall out naturally from
shared Redis: a terminal event on any replica removes the key regardless of
which replica created it.

Writes wired at the single broadcast choke point in
`app/gateway.py::_broadcast_routing_event`, which now branches on
`event_data.type` and dispatches to the new `_update_active_registry` helper.
Registry-update failures are swallowed so a Redis hiccup never breaks the
actual event broadcast/logging.

  patches the store's own namespace, asserts create/update/delete lifecycle,
  custom TTL on write, cross-pod delete semantics (two store instances), and
  list_requests excluding deleted/expired.
- Integration: `tests_integration/infrastructure/test_routing_registry_ttl.py`
  — round-trips a real write against the live session Redis with a short TTL,

## US-003 — Snapshot builder service (DONE)

Added the typed, versioned snapshot payload model and its builder:

- `app/models/routing_snapshot.py` — `RoutingSnapshot` + sub-models
  (`RoutingHost`, `InstanceStateEntry`, `ActiveRequestEntry`,
  `RequestAggregates`) with `schema_version` (1) and `generated_at`. The same
  payload is shared by the WS emit (US-004) and REST mirror (US-005).
  Field contract to the WebUI (documented in the module docstring):
  `active_requests` → requests Map, `instance_states` → instanceStates Map,
  `endpoints` → endpoints list, `aggregates` → server-computed inFlight/totals,
  `hosts`/`pending_hosts` → host status + pending-approval hosts. Exported via
  `app/models/__init__.py`.
- `app/services/routing_snapshot_builder.py` — `build_routing_snapshot()` composes
  hosts (status + drain + health + instance cache from `host_store`),
  per-instance states (`instance_states_store.get_all`), active requests
  (`routing_store.list_requests`), server-computed tallies, endpoints
  (`endpoint_db.get_all_endpoints`, shape matches `endpoints_update`), and
  pending hosts (`host_store.get_all_pending`).
- Aggregate arithmetic moved server-side (mirrors WebUI `workload.ts` /
  `graph.ts`): `by_instance` (`host:instance` cell keys), `by_host`,
  `by_model` (uses `resolved_model` with `model` fallback), `by_endpoint`,
  plus `queued`/`processing` (an entry carrying host+instance is
  `processing`, otherwise `queued`) and `errored` (0 — terminal requests are
  deleted from the registry). Endpoint loading degrades to empty on failure.

Tests: `tests/test_routing_snapshot_builder.py` (7 tests, anyio) — placeholder-shaped
snapshot, host status/drain/health + connected + instance cache, instance

## US-005 — REST snapshot mirror (DONE)

Added a REST mirror of the authoritative snapshot so the WebUI can fall back to
server state when the Socket.IO connection is down.

- New `app/routes/management/routing.py` — `GET /api/routing/state`
  (`response_model=RoutingSnapshot`), returns
  `build_routing_snapshot()` so the payload is byte-for-byte the same shape as
  the WS `routing_snapshot` event (schema_version + generated_at + all fields).
- Registered on `app/routes/management/__init__.py` via `routing.router`
  under the `/api` prefix; auth is the app-level management-key check shared by
  every management route (401 without `X-API-Key`).

Circular import fix: importing the snapshot builder directly exposed a latent
cycle (`routing_snapshot_builder` → `host_handlers` → `socketio_app/server.py` →
`webui_handlers` → `routing_snapshot_builder`). The root cause was
architectural: the builder reached into the Socket.IO presentation layer
(`host_handlers`) for three accessors that are thin wrappers over the Redis
`host_store` (`get_host_instances` → `host_store.get_host_instances`,
`get_connected_host_ids` → `host_store.get_connected_host_ids`,
`get_pending_hosts` → `host_store.get_all_pending`). Fixed structurally by
having the builder call `host_store` directly (it already imported from
`app.redis_state`), so the service no longer depends on socketio at all and the
cycle cannot form for any entry point. `test_routing_snapshot_builder.py`
patch targets updated from `app.socketio_app.host_handlers.get_*` to
`app.services.routing_snapshot_builder.host_store.get_*`.

Module named `routing_snapshot_builder.py` (a noun, matching the rest of
`app/services/`) — it assembles the authoritative `RoutingSnapshot` view-model.
The test module was renamed to `test_routing_snapshot_builder.py` to match.

Tests: new `tests/test_routing_rest.py` (2 tests) — 401 without the management
key, and 200 with the key returning the snapshot payload (schema_version,
generated_at, active_requests, hosts), patching the route's
`build_routing_snapshot` import via TestClient.

Feedback loops: ruff + black pass (ruff not executable on NixOS; verified by
review + black), full solar-control unit suite green (1040 passed).

## US-008 — Ticker backfill after snapshot (DONE)

The Routing page's live-request ticker no longer sits empty the moment a
snapshot is applied. The authoritative snapshot only carries in-flight
requests (US-003), so right after a (re)connect the ticker had no terminal
history until a fresh delta flowed. Now each applied snapshot backfills recent
terminal (`request_error`) events from `GET /api/gateway/events/recent` and
merges them with the live active-request aggregates.

- New snapshot-listener channel on the event stream, so the connected Routing
  view can react to a just-applied authoritative snapshot without overriding
  the built-in `routing_snapshot` handler:
  - `useEventStream` gains `snapshotListenersRef` and a stable
    `registerRoutingSnapshotHandler(listener)` (returns an unsubscribe);
    `snapshotListenersRef` is added to the `DispatchContext` so
    `handleRoutingSnapshot` can run registered listeners after it applies the
    snapshot (alongside the existing `h.onRoutingSnapshot` callback).
  - `eventHandlers/types.ts` adds `snapshotListenersRef` to `DispatchContext`;
    `eventHandlers/instanceState.ts` invokes every registered listener after
    applying the snapshot.
  - `EventStreamContext` / `RoutingEventsContext` expose
    `registerRoutingSnapshotHandler` in their values.
- `workload.ts`:
  - NEW `terminalRequests(events, limit)` — maps recent `request_error`
    `GatewayEventDTO`s onto `status:'error'` `RequestState` rows (model,
    host, error_message, duration, timestamp); ignores non-terminal event
    types and entries without a request_id.
  - `tickerRequests` keeps its original `(requests, limit)` signature; the
    caller passes the merged `[active, ...terminal]` list.
- `RoutingFlow.tsx`:
  - Adds `recentTerminal` state and a `backfillTerminal()` callback that calls
    `solarClient.getRecentGatewayEvents({ to: now, limit: 40, types:
    'request_error' })` and maps via `terminalRequests`.
  - Connected: subscribes via `registerRoutingSnapshotHandler(backfillTerminal)`
    so every authoritative WS snapshot refills the terminal history.
  - Disconnected: an effect keyed on each new fallback snapshot keeps the
    terminal history in step with the REST poll.
  - The ticker memo sources live in-flight rows from the existing
    `requestList` (snapshot aggregates) plus `recentTerminal`.

Tests:
- `workload.test.ts`: 3 new `terminalRequests` cases — error-event mapping,
  non-terminal types ignored, missing-request-id skipped + limit honored.
- `RoutingFlow.test.tsx`: 2 new backfill cases — (a) invoking the captured
  `registerRoutingSnapshotHandler` listener after a connected render triggers
  `getRecentGatewayEvents` and the terminal row renders in the ticker; (b) with

## US-012 — Dynamically registered event handler registry (DONE)

`useEventStream.ts` now dispatches socket events through a handler registry
keyed by `WSMessageType` instead of the single hardcoded `switch` in
`handleEvent`, so adding or overriding an event type is a one-line registration
rather than editing a growing branch.

- `registryRef` — `Partial<Record<WSMessageType, RegisteredHandler>>`, the
  dispatch table. Built-in handlers are seeded once on mount (every captured
  value — state setters, refs, and the stable `updateRequest`/`removeRequest`
  callbacks — is render-stable, so the registry never needs rebuilding).
- `registerHandler(type, fn)` — public helper (exposed on the returned hook
  object) that writes a handler into the registry; consumers can register a new
  type or override a built-in without touching the switch.
- `handleEvent` — now a stable `[]` callback that resolves
  `registryRef.current[event.type]?.(event)` and falls back to a no-op for
  unregistered event types instead of leaving a case unhandled or crashing.
- Each former `switch` case became a `register('<type>', handler)` entry with
  byte-for-byte identical behaviour. The `awaitingSnapshotRef` gating is
  preserved per `request_*`/`instance_state` handler (gated handlers `return`
  early). `keepalive` registers no handler (no-op).
- The `bindEvent` wiring in the connect effect is unchanged and still routes
  through `handleEvent` → the registry.

Follow-up refinement: the handler implementations were extracted out of
`useEventStream.ts` into the sibling `eventHandlers/` folder, so the hook is no
longer a large block of inline closures. Both live under
`apps/solar-webui/src/hooks/eventStream/` (the hook is `eventStream/`
`useEventStream.ts`, its handlers in `eventStream/eventHandlers/`):
- `types.ts` — `DispatchContext` (bundles every stable React value a handler
  touches: all 12 state setters, `awaitingSnapshotRef`/`gatewayFilterRef`/
  `handlersRef`, `updateRequest`, `removeRequest`) and `RegisteredHandler`
  (`(event, ctx) => void`).
- Per-domain files: `request.ts` (request_start/routed/success/error/reroute),
  `hosts.ts` (initial_status/host_status/host_pending/host_pending_removed/
  instances_update/host_health), `instanceState.ts` (log/instance_state/
  routing_snapshot), `gateway.ts` (gateway_request/filter_status/
  endpoints_update/api_keys_update), `intents.ts` (intent_update/intent_removed),
  `pulls.ts` (pull_progress).
- `registry.ts` — `buildRegistry()` composes every built-in handler into the
  `Partial<Record<WSMessageType, RegisteredHandler>>` seed.
- `pullProgress.ts` — pull-progress types/constants/`prunePullProgress` moved
  here from `useEventStream.ts` to break the runtime circular import
  (useEventStream → registry → pulls → useEventStream); `useEventStream.ts`
  re-exports them so consumers (`IntentDetail`, `IntentsPage`,
  `PullProgress.test`) are unchanged.
- Directory layout: `src/hooks/eventStream/useEventStream.ts` +
  `src/hooks/eventStream/eventHandlers/{types,registry,request,hosts,
  instanceState,gateway,intents,pulls,pullProgress}.ts`; all consumers'
  `@/hooks/useEventStream` imports updated to `@/hooks/eventStream/useEventStream`.
- `useEventStream.ts` now builds a stable `DispatchContext` (`useMemo`) once,
  seeds the registry via `Object.assign(registryRef.current, buildRegistry())`
  on mount, and `handleEvent` dispatches `(event, ctx)`. `registerHandler`
  still takes a plain `(event) => void` for external consumers; built-in
  handlers use the richer `(event, ctx)` signature.

Tests (`apps/solar-webui/src/hooks/__tests__/useEventStream.test.ts`):
- New: (a) a consumer-registered handler (`registerHandler('host_status', fn)`)
  is dispatched for a bound socket event; (b) an event type with no registered

- Existing US-006 snapshot consumer tests pass unchanged, proving the refactor

## US-009 — Derive routing view from snapshot aggregates (DONE)

The Routing page's load bars and totals are now computed from the authoritative
server snapshot aggregates instead of being re-derived from the transient client
request Map.

Backend (US-003) already produced a `RequestAggregates` payload (`by_instance`,
`by_host`, `by_model`, `by_endpoint`, `queued`, `processing`, `errored`) on every
snapshot; the WebUI stored nothing but the request/state Maps, so those tallies
were ignored. This story threads the aggregates through and makes them the
source of truth for the cell loads and the header/gateway numbers.

- `useEventStream.ts`:
  - Adds an `aggregates` state (`RoutingStateAggregates | null`), exposed on the
    returned hook.
  - Adds `setAggregates` to the `DispatchContext` passed to handlers.
  - Resets `aggregates` to `null` on socket connect, alongside the existing
    request/instance-state/endpoint reset.
  - re-exports `RoutingStateAggregates` from `@/api/types`.
- `eventHandlers/types.ts`: `DispatchContext` gains `setAggregates`.
- `eventHandlers/instanceState.ts` `handleRoutingSnapshot`: after applying the
  snapshot, stores `snap.aggregates ?? null` so the connected view always has
  the server-correct tallies.
- `EventStreamContext.tsx` / `RoutingEventsContext.tsx`: both expose
  `aggregates` in their context values.
- `RoutingFlow.tsx`: derives `aggregates` per mode — connected mode uses the
  WS-seeded `wsAggregates` from the routing context, disconnected mode the REST
  mirror's `fallback.aggregates` — and passes it to `buildFlowGraph` and
  `summarizeFlow`.
- `workload.ts`:
  - `buildCells` accepts an optional `aggregates`; when present the cell
    `inFlight` reads `aggregates.by_instance["host:instance"]` instead of
    `countInFlightByInstance(requests)`; otherwise it falls back to the Map.
  - `summarizeFlow` accepts an optional `aggregates`; `pending`/`processing`/
    `errored` come from `queued`/`processing`/`errored`. Host/instance counts
    still come from `hosts` (the aggregates carry no per-host fleet topology).
- `graph.ts`:
  - `buildFlowGraph` accepts an optional `aggregates` and passes it through to
    `buildCells` and `tallyTraffic`.
  - `tallyTraffic` with aggregates present: seeds `by_endpoint`/`by_model` from
    `by_endpoint`/`by_model`, derives the model→host binding loads from
    `by_instance` grouped per host, and takes `queued`/`processing`/`errored`
    from the aggregates. Per-hop `errors` (the red error tone) still come from
    the request Map because the aggregates carry only an aggregate `errored`
    total, not a per-hop breakdown. Without aggregates it falls back to the
    prior request-Map tally, preserving backward behaviour.

View-only concerns (search, expand/collapse, host selection, trace traversal,
layout) stay client-side, per the contract.

Tests (`apps/solar-webui/src/components/routing/__tests__`):
- `workload.test.ts` (+3): `buildCells` reads per-cell load from
  `aggregates.by_instance` with a deliberately empty request Map; `buildCells`
  falls back to the Map without aggregates; `summarizeFlow` uses the server
  totals instead of tallying the client Map; spread of host/instance counts
  alongside aggregate totals.
- `graph.test.ts` (+3): `buildFlowGraph` weights the endpoint/model/host hops
  and the gateway tallies from the aggregates with an empty request Map; keeps
  per-hop error tone from the request Map while the in-flight load comes from
  the aggregates; does not double-count the aggregate `errored` total when error
  requests are present.

Feedback loops: `tsc --noEmit` clean, `pnpm lint` (eslint 0 errors + prettier)
green, full webui vitest suite green (520 passed). No new US-* references in
code.

## US-010 — Remove obsolete client-side routing aggregation (DONE)

The routing view now derives every load bar and total from the authoritative
