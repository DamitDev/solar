# U-006: Add intent editing to the Solar WebUI

## Description

U-003 built the intent submission form and the live status views. Changing an existing deployment is not possible: the intent list and detail pages offer only delete, and the detail page tells the operator outright that a change requires delete plus recreate. That is the worst available option for a `production` deployment, because it stops every replica before the replacement starts — the downtime the `rolling` strategy exists to avoid — and it discards the intent's identity and history.

S-044 adds `PUT /api/intents/{id}` with full-replace semantics: the same schema as create, `alias` immutable, and a reset of the in-flight rollout so the edited spec is what gets rolled out under the strategy named in the edit. This issue exposes that in the WebUI.

The submission form is close to reusable but not reusable as it stands. It hydrates only a handful of fields from its `initial` prop, and always initialises the backend section from defaults rather than from an existing intent — so opening it on an existing deployment would silently reset the backend configuration, placement constraints, resource hints and metadata to defaults, and saving that would be a destructive no-warning change.

## Goal

- Add a typed client method and request type for the update endpoint.
- Generalise the existing intent form into one component with create and edit modes rather than duplicating it, so a field added to submission is never missing from editing.
- In edit mode, hydrate **every** field from the existing intent: alias, model source, replicas, priority, strategy, the full backend configuration (including the model file and download filter fields, which live inside the backend object), placement constraints, resource hints and metadata. A field the operator does not touch must round-trip unchanged, which matters because the endpoint is full-replace.
- Present alias as read-only in edit mode and explain why (it is the served name and the deployment's identity; a different name is a different deployment).
- Switch the title, submit label and success handling per mode.
- Warn before saving when a rollout is currently in flight, since saving restarts it against the new spec. The intent status already reports rollout progress, so the warning can be driven from it.
- Add Edit entry points on both the intent detail page — replacing the note that says updates are not implemented — and the intent list.
- Reuse the existing client-side validation for the update path, and surface the server's structured validation errors and conflicts the same way submission does. The server stays authoritative.
- Make it clear what an edit will do, so nobody has to guess whether saving causes downtime: the strategy field in the form is the one that governs the resulting rollout, and it is worth restating that `immediate` briefly stops the replicas while `rolling` does not.
- Add unit tests in the existing vitest suite for the edit-mode hydration round-trip (an untouched form produces a request equal to the loaded intent) and the alias-immutability and rollout-warning behaviour, and run the lint step.
