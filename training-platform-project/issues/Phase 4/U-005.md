# U-005: Add host draining controls to the Solar WebUI Resources page

## Description

The Resources page from U-004 is read-only: it shows each host's capacity breakdown, roles, GPU type, online/offline status and the workloads behind every bar, but offers no action. Taking a host out of service for maintenance therefore happens outside the WebUI, and before S-043 it had no correct path at all.

S-043 makes draining a first-class host state in Solar Control: an operator marks a host as draining, placement stops choosing it, and the reconciler migrates the intent-managed replicas away one at a time until the host is empty. Two properties of that design need UI support rather than a plain confirm dialog:

- A drain **cannot start** while manually created instances are still running, because those have no desired state to reconcile and Solar Control will not move someone else's workload. The operator has to stop them first, so the UI must name them instead of returning an opaque error.
- A drain **can stall**. If no other host can accept a replica, the replica keeps serving and the host stays in `draining` indefinitely. That is deliberate — a drain never reduces serving capacity — but it means "draining" and "stuck draining" must be visually distinguishable, with the reason shown.

The Resources page is the right home: it already knows every host, is already live via Socket.IO, and already shows the instances that determine whether a drain can start.

## Goal

- Add typed client methods and types for the three S-043 endpoints (start drain, cancel drain / resume, read drain progress), alongside the existing host and resource methods.
- Show drain state on each host card as a badge distinct from the online/offline status badge, since a draining host is still online. Cover not draining, `draining`, `drained`, and the stalled case.
- Add a Drain action to the host card, and a Resume action for a host that is `draining` or `drained`.
- Use a confirmation modal for the drain, in the style of the existing intent delete modal, which:
  - explains what will happen (managed replicas migrate away; the host accepts no new work until resumed),
  - lists the manual instances that must be stopped first, fetched from the drain progress endpoint, and keeps the confirm button disabled while any remain,
  - lists blocking job steps for the same reason,
  - surfaces the server's structured `409` blockers inline if the preflight fails anyway (the state can change between opening the modal and confirming),
  - shows a loading state and does not close on error.
- While a host is draining, show progress where the workloads already live on the card: how many managed replicas remain, and for any replica that cannot be moved, the reason reported by the API. A stalled drain must read as needing operator attention, not as being in progress.
- Keep the view current from the existing Socket.IO host status event, which S-043 extends with the drain state, so a drain that progresses on another operator's screen updates here too. Fall back on the page's existing periodic refetch.
- Do not reimplement any of the policy client-side. Whether a drain may start, which instances block it and why a replica cannot move are all answered by the API; the UI renders those answers. In particular do not decide client-side that a manual instance is "probably fine" to leave running.
- Follow the existing conventions: Nord theme classes, `lucide-react` icons, `cn()` and the helpers in `src/lib/utils.ts`, so the badges and buttons match the rest of the page.
- Add unit tests in the existing vitest suite for the modal's gating on blockers and for the badge/stall rendering, and run the lint step.
