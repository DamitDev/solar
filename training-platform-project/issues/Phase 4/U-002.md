# U-002: Add model catalog view to Solar WebUI

## Description

Solar WebUI today has no concept of a model catalog. Its pages are `/routing` (live request graph), `/gateway` (request statistics), `/hosts` (hosts and instances), and `/endpoints` (API keys). The only model-like listing is `GET /v1/models` from the inference gateway, which reflects what is *currently served* — not what exists in the Data Repository and could be deployed.

Operators need to answer "what models do we have, which versions, and where are they running?" from the operations UI. D-018 provides exactly this on the Solar Control side: `GET /api/catalog/models` proxies the Data Repository model list (D-013) and enriches each entry with Solar runtime context (running instance count, deployed hosts, availability on hosts).

This issue adds the Solar WebUI catalog page that consumes that endpoint. The Data Repository stays the authority for catalog metadata; Solar Control is the only API the WebUI talks to. The catalog is also the natural entry point for deploying a model, which is why it pairs with the intent submission UI in U-003.

## Goal

- Add a new `Catalog` route and page to Solar WebUI (e.g. `/catalog`), registered in the router and the top navigation alongside Routing / Gateway / Hosts & Instances / Endpoints.
- Add a typed API client method for D-018's `GET /api/catalog/models` in `src/api/client.ts`, plus catalog types in `src/api/types.ts` (model summary, version summary, availability/deployment enrichment).
- Render the model list with the Data Repository summary metadata returned by D-018: name, category/type, description, version count, latest version, created/updated timestamps.
- Render the Solar enrichment per model: running instance count, host names where it is deployed, availability on hosts, and an overall deployment/availability status badge.
- Support the endpoint's search and pagination parameters (`search`, `limit`, `offset`) with UI controls, keeping `total` from the response for pagination.
- Add a model detail view (page or expandable row/panel) showing version information and full metadata for the selected model, using only the data D-018 returns.
- Handle the degraded states D-018 defines explicitly, without misleading the operator:
  - Data Repository unreachable → clear error state, not an empty catalog.
  - Missing/`unknown` availability enrichment (when S-020 is not yet available) → render availability as unknown rather than as "not available".
  - Empty catalog → distinct empty state.
- Provide a "Deploy" affordance per model that hands off to the U-003 intent form, pre-filling alias and `model_source` (`repo://{name}:{version}`). If U-003 is not merged yet, the affordance may be omitted or disabled — do not implement a parallel deployment path here.
- Follow existing UI conventions: Nord theme classes, `lucide-react` icons, `cn()` from `src/lib/utils.ts`, loading/error patterns from `Dashboard.tsx` / `GatewayDashboard.tsx`, and the cards/table view-mode toggle pattern if a table view is added.
- Run the repo's `npm run lint` (ESLint + Prettier) and verify the page against a running Solar Control.

## Additional Notes

- Repo: `solar-webui` at `/mnt/nvme/AI/damit-aiops/solar/apps/solar-webui`
- Key files: `src/App.tsx` (router + `Navigation`), `src/api/client.ts`, `src/api/types.ts`, new `src/components/ModelCatalog.tsx` (and detail component), `src/lib/utils.ts` for formatting helpers.
- API: `GET /api/catalog/models` from solar-control (D-018). The WebUI reaches Solar Control through the existing `/api/control` proxy (`vite.config.ts` in dev, `server/index.js` in production), which injects the management API key — no new proxy target or credential is needed.
- Depends on D-018 (catalog endpoint in solar-control). D-018 in turn depends on D-013 (Data Repository search/browse) and practically on S-020 (model availability per host).
- Related: U-003 (intent submission UI) is the deploy target for the catalog's deploy affordance. U-001 (training activity indicators) and U-004 (resource dashboard) are sibling Phase 4 WebUI issues.
- **Topology constraint:** Solar WebUI must not call the Data Repository API directly. Everything comes through Solar Control. If the page needs per-version detail that D-018 does not return (e.g. full version history from D-012, lineage/eval metrics from D-011), that is a request to extend D-018 — raise it with the supervisor instead of adding a Data Repository client to the WebUI.
- Scope note: the SuperNova WebUI model browser (W-007) is a separate, training-oriented view. This issue is the operations-oriented catalog and should stay focused on "what exists and where is it running".
