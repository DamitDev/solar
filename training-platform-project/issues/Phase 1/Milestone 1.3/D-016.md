# D-016: Complete `repo://` resolver in solar-control

## Description

Solar Control currently has a `repo://` resolver stub from S-013. This issue completes that resolver by calling the Data Repository resolve endpoint from D-014, obtaining the authoritative metadata and `harbor_ref`, and instructing Solar Host to pull the model directly from Harbor via `POST /models/pull`.

The Data Repository remains the authority for `repo://` metadata and resolution. Solar Control parses and resolves the URI, selects or targets a Solar Host, and sends the resolved pull instruction onward. Solar Host performs the Harbor pull directly using ORAS / `harbor-oci-client` and caches the result by the `source_uri` manifest. Solar Control must not proxy model blobs and must not duplicate ORAS or Harbor pull logic.

## Goal

- Complete the `repo://` resolver path in `solar-control` at `/mnt/nvme/AI/damit-aiops/solar/apps/solar-control`.
- Call Data Repository's D-014 resolve endpoint for URIs such as `repo://iris-osl:v3` and consume its returned `harbor_ref`, category, name, version, size, checksum, and metadata.
- Follow the final D-014 / `docs/specs/model-source-uri.md` rule for `latest`; do not invent separate `latest` behavior in Solar Control.
- Validate that resolved artifacts are deployable models before sending them to Solar Host.
- Send a pull request to the selected Solar Host via `POST /models/pull`, passing the original `source_uri` and the resolved Harbor reference/metadata needed by the host-side pull implementation.
- Preserve the architecture boundary: Solar Host pulls from Harbor directly and owns local cache state; Solar Control only resolves, routes, and instructs.
- Surface clear errors for invalid URI syntax, Data Repository unreachable, artifact/version not found, unsupported category, Solar Host unreachable, and Solar Host pull failure.
- Add or update focused tests for successful resolve-and-pull, Data Repository failure, 404/not found, non-model artifact rejection, and `latest` handling according to D-014.
