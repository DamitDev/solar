# S-032: Implement job step submission proxy in solar-control

## Description

Solar Control needs to accept job step execution requests, select an appropriate Solar Host, and proxy the request to that host's `POST /jobs` API. This preserves the required topology: SuperNova orchestrates by calling Solar Control, Solar Control routes/proxies/aggregates, and Solar Host executes containers.

Solar Control should also forward job lifecycle and log events from hosts to clients. Event forwarding readiness from S-025 and S-026 should be accounted for even though the formal dependencies are the host job API and host filtering.

## Goal

- Implement a Solar Control API endpoint for job step submission, likely under `/api/jobs` or another existing management namespace.
- Select eligible hosts by role and available resources using S-006 host status data.
- Proxy validated job payloads to the selected Solar Host `POST /jobs` endpoint from S-027.
- Provide `GET`/cancel proxy behavior if included in the endpoint design, or document follow-up coverage if scoped separately.
- Forward or rebroadcast S-025 `step_log` and S-026 lifecycle events to connected clients with job ID, host ID, and correlation metadata.
- Return clear errors when no training-capable host is available, host submission fails, or the payload is invalid.

## Additional Notes

- Repo: `solar-control` at `/mnt/nvme/AI/solar/solar-control`
- Key files likely: job routes, host selection/service layer, Solar Host client, Socket.IO event forwarding.
- Depends on S-027 (Solar Host job API) and S-006 (role/resource-aware host status).
- Should be designed with S-025/S-026 event forwarding readiness in mind.
- Consumed by SuperNova Control job orchestration and Solar WebUI job monitoring.

### S-021 Workspace Reference

The `/mnt/nvme/AI/damit-aiops/training-platform-project/docs/specs/job-step-workspace.md` informs the job payload Solar Control constructs and proxies:

- **Job payload construction:** Solar Control translates SuperNova job intents into the host-level job config (Section 5.2 of workspace spec). This includes deriving per-step environment variables (Sections 4.3) from the higher-level job description.
- **Host selection:** Choose a host with `role=training` and sufficient disk space on `JOBS_DIR`. The workspace spec requires a pre-creation disk check; Solar Control can pre-filter by querying host disk info.
- **Forwarded events:** `step_log` (S-025) and lifecycle events (S-026) include `job_id` and `host_id`. Solar Control rebroadcasts to clients with correlation metadata. The workspace layout's `logs/` directory is the authoritative log source on the host; events are the real-time stream.
- **Cancellation:** `DELETE` proxied to the host triggers immediate workspace cleanup per the lifecycle rules (Section 6.3).
