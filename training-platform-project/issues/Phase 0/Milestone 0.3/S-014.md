# S-014: Implement `GET /models` on solar-host

## Description

Solar Host has no API to list model files. Instance configs reference models by path (`model`) or HuggingFace ID (`model_id`), but there is no programmatic way to discover what models exist on a host. Solar Control's HuggingFace resolver (S-012) needs to check if a model is already present before downloading. The model availability query (S-020) and distribution (S-019) also depend on listing models across hosts.

S-009 introduces the managed models directory and manifest. This issue exposes that data via REST.

## Goal

- Implement `GET /models` endpoint on solar-host. Route under `/models` (ensure it does not conflict with OpenAI `/v1/models` if that exists; solar-host has `/instances`, so `/models` is a new top-level path).
- Response: list of models in the managed models directory. For each model: `name` (identifier, e.g. slug or directory name), `path` (absolute path), `size_bytes` (total size of model files), `source_uri` (if in manifest), `checksum` (if in manifest), metadata from manifest.
- Source data: read from manifest (S-009) and optionally cross-check with directory scan for models not yet in manifest (e.g. manually placed files).
- Require API key authentication (same as other solar-host endpoints; `/models` is not in the public paths list in `verify_api_key` middleware, so it will require `X-API-Key`).
- Return empty list if models directory or manifest does not exist yet.

## Additional Notes

- Repo: `solar-host` at `/mnt/nvme/AI/solar/solar-host`
- Key files: `app/main.py` (include new router), new `app/routes/models.py` or add to existing routes
- Depends on S-009 (managed models directory, manifest).
- Used by S-012 (cache check), S-017 (in-use check), S-019, S-020.
