# S-048: Add catalog delete relay to Solar Control

## Description

The catalog is read-only today: an artifact pushed to Harbor and registered in the Data Repository cannot be removed from the product. S-048 adds the delete relay to Solar Control, mirroring the upload relay (S-047): Solar Control deletes the Harbor artifact first, then unregisters the metadata in the Data Repository.

Harbor-first ordering is deliberate: if the unregister fails after Harbor succeeded, a retry still converges because the Harbor tag delete tolerates a missing tag (404), whereas the reverse order would orphan a blob with no reference to find it by. Deleting a version served by a running instance is refused with 409 (blocking instances listed); a version that is only cached on hosts can be deleted. Whole-repository delete returns per-version results (`deleted`, `failed`) plus `artifact_removed` and `harbor_repository_removed` flags, because a multi-version delete can partially fail.

The robot account may delete artifacts but not repositories; `OciPushClient.delete_repository()` is therefore best-effort (403/404 tolerated) and its outcome is reported.

## Goal

- Add `OciPushClient.delete_repository(repo)` to `app/harbor/oci_push.py` — `DELETE /api/v2.0/projects/{project}/repositories/{repo_name}`, best-effort: 200/202/404 → success, 403 → tolerated (reported as not removed), other → logged and reported as not removed. Does not raise for permission failures.
- Add `DataRepoClient.delete(path)` to `app/services/uploads.py` (protocol + `AioHttpDataRepo`).
- New `app/services/catalog_delete.py` with `CatalogDeleteService`:
  - `delete_version(name, version)`: validate name; reject `version == "latest"` (422, mirrors Data Repository's reserved-alias rule); `GET /api/models/{name}/versions/{version}` → 404 propagated; guard → 409 with blocking instances; `OciPushClient.delete_tag(parse_repo(harbor_ref), version)` → `OciPushError` becomes 502 with metadata untouched; `DELETE /api/models/{name}/versions/{version}` — 204 and 404 both count as success.
  - `delete_artifact(name)`: `GET /api/models/{name}/versions` (one call; `ModelVersionListItem` already carries `harbor_ref`); guard across all versions; `delete_tag` per version collecting failures; unregister each tag that was removed; when all versions are clean → `DELETE /api/models/{name}` (cascade) and best-effort `delete_repository()`; any Harbor failure leaves the artifact row in place and returns per-version failures so the user can retry.
- Extract the running-instance collection already in `app/routes/management/catalog.py` (`_collect_running_instances`) into a version-aware guard. `RepoURI` already exposes `.version`; match `repo://{name}:{version}` and treat `repo://{name}:latest` as matching the artifact's newest version. Only running instances block; host-cached copies do not.
- Routes in `app/routes/management/catalog.py`:
  - `GET /api/catalog/models/{name}/versions` — proxy plus per-version `solar` block (`running_instances`, `deployed_hosts`) so the UI can show what blocks each row. `_fetch_models_from_host` already receives `version` from the host manifest (D-016); start reading it.
  - `DELETE /api/catalog/models/{name}/versions/{version}` → 204.
  - `DELETE /api/catalog/models/{name}` → 200 with `{name, deleted: [...], failed: [{version, detail}], artifact_removed, harbor_repository_removed}`.
- Update the management endpoint list in `app/main.py`.
- `harbor_repository_removed` semantics: `true` when the repository DELETE succeeded (200/202) or the repository is already gone (404); `false` when forbidden (403) or any other status. Note: real Harbor auto-removes an empty repository after its last artifact is deleted, so 404 is the normal outcome after a successful artifact delete — the flag reports the repository's absence, not whether the robot account holds the permission.
