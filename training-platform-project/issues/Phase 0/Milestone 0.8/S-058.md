# S-058: Make inference, placement and reservations GPU-aware

## Description

Solar treats each host as one aggregate VRAM pool: the host sums all GPUs
into a single used/total number (`memory_monitor._get_nvidia_memory`),
placement checks that one number (`placement.fits_resources`), and the
backend process is launched without any device selection. On a multi-GPU
host (e.g. ai04, 3x RTX PRO 6000) this is wrong in both directions: an
instance lands on device 0 by default even when another device is free, and
a host can report aggregate free VRAM while no single device can fit the
model. The llama.cpp multi-GPU flags (`devices`, `split_mode`,
`tensor_split`, `main_gpu`) and sglang `tp_size` exist but are raw physical
indices; nothing selects or enforces which devices a process actually uses.
Reservations (S-034 host-side, reconciler cold-start) are likewise
aggregate and unknown per device.

This issue makes Solar GPU-aware end to end. Hosts report per-GPU
telemetry, intents declare `gpu_count` (default 1), solar-control picks the
exact physical devices via a shared per-GPU placement helper, and
solar-host enforces the choice with `CUDA_VISIBLE_DEVICES` plus a
spawn-time re-verification. The intent stays declarative — physical device
ids are never user-settable.

## Goal

- **Host telemetry:** add per-device GPU reporting to solar-host
  (`memory_monitor.get_gpu_list()` via pynvml per device:
  index, name, total_gb, used_gb, available_gb). Include `gpus` in the
  `/resources` response and the WS health/resource push; add
  `gpus: list[GpuInfo]` to solar-control `HostResourceSnapshot`. Hosts
  without a GPU list (old agents, Mac, CPU) fall back to today's aggregate
  behavior — nothing regresses during rollout.
- **Intent contract:** add `gpu_count: int = 1` to
  `ResourceRequirements` (solar-control `app/models/intent.py` + webui
  mirror). `vram_gb` becomes a per-GPU footprint (default `gpu_count: 1`
  keeps single-GPU intents identical). Validation derives the count from
  backend fields when not explicit (sglang `tp_size`, llama.cpp `devices`
  list length / `tensor_split` count) and 422s on mismatch. Backend device
  fields keep meaning as positions within the scheduler-chosen set, not
  physical indices.
- **Placement:** add `find_gpu_assignment(snapshot, gpu_count, vram_gb)
  -> list[int] | None` to `app/services/placement.py`, shared by the
  reconciler and the S-038 coordinator. Per-device availability counts host
  nvidia-smi free minus host-side reservation headroom minus control-side
  cold-start claim hashes, so concurrent intents cannot double-book a
  device. Preference: most free memory first, lowest index tie-break.
- **Reservation and lifecycle:** cold-start reservation (per-intent Redis
  hash) gains `gpu_ids`, chosen with placement and held through the model
  pull; instance create carries `gpu_ids` to the host; stop/delete releases
  the claim. Both `ReservationRequest` models (control + host) gain
  `gpu_count`; host `ResourceManager` accounts per device,
  `CapacityExceededError` names the failing device; reservation responses
  carry `gpu_ids`. Migration/evacuation/displacement re-run
  `find_gpu_assignment` on the target and thread `gpu_ids` through
  `execute_migration` / `execute_evacuation`.
- **Enforcement:** each backend runner's `build_env` sets
  `CUDA_VISIBLE_DEVICES` to the chosen physical indices (llama.cpp, sglang,
  HuggingFace). Before child spawn, solar-host re-verifies per-device free
  memory and fails fast, naming the device, if a foreign process took it;
  the reconciler's existing backoff/replacement handles the retry.
- **WebUI (minimal):** per-GPU cards on the resources page, `gpu_count`
  input on the intent form with a note that physical selection is
  automatic, assigned devices on instance/storage rows.
- **Docs:** update `docs/specs/deployment-intent.md` §4.6 (gpu_count,
  per-GPU vram_gb) and §8.4 (per-GPU placement and ranking).
- **Tests:** unit — bin-packing, derived vs explicit count validation,
  unified-memory folding, double-booking prevention, env injection,
  spawn-time fail-fast; integration — stub host with a 3-GPU list places an
  intent on the free device, spawns with `CUDA_VISIBLE_DEVICES=2` and
  reports `gpu_ids`; training reservation holds chosen devices; migration
  carries `gpu_ids` to the target.
- **Spike before implementation:** on ai04, verify llama.cpp honors
  `CUDA_VISIBLE_DEVICES` for `--device`/`--main-gpu` ordering and sglang TP
  serves correctly from a reordered subset.
