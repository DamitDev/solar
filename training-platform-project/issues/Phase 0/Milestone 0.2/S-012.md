# S-012: Implement `huggingface://` resolver in solar-control

## Description

Solar Control has no HuggingFace model download capability. HuggingFace-backed instances today require the model to be pre-downloaded on the host (or use `model_id` with HuggingFace's automatic download at runtime). The model source abstraction requires solar-control to resolve `huggingface://` URIs by instructing the target Solar Host to pull the model directly from HuggingFace Hub.

Following the Kubernetes model (hosts pull directly from sources, control plane orchestrates), Solar Control sends a pull command to Solar Host, which downloads the model itself. This avoids proxying multi-GB model files through Solar Control.

## Goal

- Implement the `huggingface://` resolver in solar-control. Input: URI (e.g. `huggingface://microsoft/phi-3`), target `host_id`.
- Resolver logic: (1) Parse URI to extract model ID (e.g. `microsoft/phi-3`). (2) Call `POST /models/pull` on target Solar Host with `{source: "huggingface", model_id: "microsoft/phi-3", source_uri: "huggingface://microsoft/phi-3"}`. (3) Solar Host handles cache check, download (if needed), and manifest update. (4) Receive resolved local path from Solar Host. (5) Return `local://{path}` for instance creation.
- Solar Host handles caching autonomously: if the model is already in the manifest, it returns the cached path immediately without downloading.
- Handle errors: Solar Host returns structured errors for HuggingFace API failures (404, auth), disk full (507), credential issues (missing `HF_TOKEN`). Propagate these to the dispatcher with context.
