# S-004: Add available VRAM/RAM calculation to `/memory` endpoint

## Description

Solar Host's `/memory` endpoint returns `used_gb`, `total_gb`, `percent`, and `memory_type` from `memory_monitor.get_memory_info()`. It does not compute or report *available* memory (total minus used by running instances). The `host_health` Socket.IO event includes `running_instance_count` but not per-instance memory usage.

SuperNova needs to know how much VRAM/RAM is free for new instances or training jobs. The current "used" reflects system-wide usage; we need `available = total - used_by_running_instances` (or a reasonable approximation).

## Goal

- Extend the `/memory` endpoint response with an `available` field.
- Compute `available` as `total - used_by_running_instances`. This requires tracking memory usage per running instance. Options: (a) sum known instance allocations from config (e.g. `n_gpu_layers`-based estimates), (b) use `total - used` from pynvml/psutil as a simpler approximation (current "used" already reflects running processes), or (c) query each instance's memory if backends expose it.
- Document the semantics: `available` = memory that can be allocated to new workloads.
- Include `available` in the `host_health` event payload for solar-control.

## Additional Notes

- Repo: `solar-host` at `/mnt/nvme/AI/solar/solar-host`
- Key files: `app/main.py` (`get_memory`), `app/memory_monitor.py`, `app/ws_client.py` (`send_health`)
- `MemoryInfo` model in solar-control (`app/models.py`) and solar-host (`app/models/base.py`) may need an `available_gb` field.
