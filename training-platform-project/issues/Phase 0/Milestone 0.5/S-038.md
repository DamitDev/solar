# S-038: Implement resource reservation coordinator in solar-control

## Description

SuperNova needs a single Solar Control operation that can answer "reserve resources for this job" without knowing about individual Solar Hosts. Solar Control must evaluate host resources, roles, reservations, priorities, and migration options, then return an assigned host or a clear error.

This issue implements the cluster-level reservation coordinator. Solar Host remains responsible for local reservation primitives; Solar Control owns placement, migration coordination, and policy.

## Goal

- Implement a Solar Control API for resource reservation requests, such as `POST /api/resources/reservations`.
- Accept requested resources, required host roles, GPU type/constraints, workload type, requester/job identifier, and optional duration/TTL.
- Query aggregated resources from S-035 and choose a suitable host using a documented placement policy.
- Use `available = total - Σeffective` (the per-host `effective` semantics from S-034/S-035) when evaluating capacity.
- If no host is immediately available, evaluate whether lower-priority instances can be migrated through S-037 to satisfy the request.
- Call the selected Solar Host reservation API from S-034 and return reservation id, host assignment, expiration, and resource details.
- Provide release/cancel support, such as `DELETE /api/resources/reservations/{id}`, routed through Solar Control.
- Return deterministic failure reasons when capacity cannot be reserved.
- Preserve one replica per host for the same deployed model/alias when migrations are considered as part of freeing capacity.
