# S-050: Host resource snapshot over the WS push plus the Redis read model

## Description

Control proxied `GET /resources` from every host on every reconcile tick,
per host, per tick. The host already pushed a health summary over the WS
channel every 10 seconds, but the summary deliberately omitted the
per-reservation list (decision O4), so the API had to fall back to HTTP to
show reservations. This made the resources view slow and fragile when a
host was briefly unreachable.

## Goal

- The host's `host_health` push carries the full resource snapshot
  (`resources` block, byte-identical to the host's `GET /resources`),
  alongside the legacy summary keys for older control versions.
- Control stores it in Redis (`solar:hosts:snapshots`, value
  `{"at": <iso8601>, "resources": {...}}`) as the WS-first read model.
- `_fetch_host_resource_snapshot` serves cache-first when the host is
  connected and the entry is younger than `settings.host_snapshot_max_age_s`
  (`snapshot_source: "ws"`); HTTP proxying remains the degraded fallback
  (`snapshot_source: "http"`, or `"none"` with an error when unreachable).
- Endpoint records are event-driven: control emits `endpoints_update` on
  endpoint create/update and the webui consumes it (REST is a fallback).
