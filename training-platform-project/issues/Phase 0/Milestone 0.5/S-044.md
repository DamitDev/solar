# S-044: Implement intent update endpoint in solar-control

## Description

S-040 shipped the intent API as create, list, get and delete. Changing an existing deployment — scaling replicas, rolling out a new model version, switching strategy, correcting a backend parameter — has no supported path. `docs/specs/deployment-intent.md` §12.5 documents the intended `PUT /api/intents/{id}` and defers it; the integration tests work around it by writing the `intents` row directly (`tests_integration/fixtures/seed.py`), and the WebUI tells the operator that "changing a deployment requires delete + recreate".

Delete + recreate is the wrong answer for `production`: it stops every replica before the new ones start, which is exactly the downtime the `rolling` strategy exists to avoid. It also loses the intent's history and identity.

The reconciliation side is largely ready. S-041 detects drift between the intent's `model_source` and its running replicas, S-042 converges through the `rolling` and `immediate` strategies, and replica-count changes already flow through the normal diff. What is missing is a validated, audited entry point that writes the spec — plus a handful of update-specific behaviours the reconciler does not have today, because until now a spec never changed under it.

The important one: when a strategy is in flight, the reconciler bypasses the normal diff and drives the state machine stored in `status.strategy_progress`, which carries the target model source captured when the strategy was *initiated*. An edit that lands mid-rollout would leave the rollout converging on the superseded target. The update path has to reset that progress so the strategy re-initiates against the new spec.

## Goal

- Add `PUT /api/intents/{id}` accepting the same request schema as create, with full-replace semantics: fields absent from the request fall back to their documented defaults, exactly as on create, so the stored spec always equals what the client sent.
- Treat `alias` as identity: reject a request that would change it. Serving a different name is a different deployment, not an edit of this one.
- Share validation with create so the two cannot drift apart. Every rule that rejects a bad intent on submission must reject it on update.
- Reject an update to an intent that is being deleted, and return the usual not-found for unknown or already-deleted intents. Keep the alias-conflict check, excluding the intent being updated from the comparison.
- Reset `status.strategy_progress` when the spec actually changed, so a subsequent rollout is planned from the new spec rather than continuing toward the superseded target. The strategy value in the updated spec is the one that governs the resulting rollout.
- Wake the reconciler on a successful update so the change is picked up immediately rather than on the next periodic tick.
- Make the reconciler safe against a spec that changes underneath it:
  - Load the intent fresh inside the per-intent lock, so a pass that started before the update cannot act on the stale spec.
  - Invalidate a recorded failure backoff when the spec changes, so an edit that fixes a broken deployment is retried at once instead of waiting out the backoff earned by the previous spec.
  - Detect drift for backend-only edits. Current drift detection compares the intent's backend against the flat instance cache and skips keys the cache does not carry, so several backend fields could change without any replica being replaced. An update must be able to roll out a backend change, using the full instance configuration for the comparison when a spec change is pending.
- Confirm the existing multi-replica protection is sufficient for the new path: reconciliation is already serialised per intent by a Redis lock, so two Solar Control replicas cannot act on the same intent concurrently. Document the conclusion rather than adding a second locking mechanism.
- Cover with unit tests: update validation including alias immutability, the strategy-progress reset, rejection while deleting, backoff invalidation on a spec change, and drift detection for a backend-only edit. Switch the integration tests that currently mutate the `intents` row to the real endpoint.

## Additional Notes

- Repo: `solar-control` at `/mnt/nvme/AI/damit-aiops/solar/apps/solar-control`
- Specification: `docs/specs/deployment-intent.md` §12.5 defines the endpoint contract, §8 the reconciliation/drift behaviour, §11 the strategies. The spec's §16 listing of the update endpoint as a future extension is removed by this issue.
- Key files: `app/models/intent.py` (`IntentCreate`, add the update model), `app/validation.py` (`validate_intent_create` — extract the shared rules), `app/database/intents.py` (`IntentDB.update_status` exists for server-managed fields only; spec-field updates are new; `check_alias_conflict` already accepts `exclude_id`), `app/routes/management/intents.py`, `app/services/reconciliation.py` (`_reconcile_one`, `_get_strategy_progress`, `_detect_backend_drift`, backoff helpers), `app/services/strategies.py`, `tests_integration/fixtures/seed.py`.
- Depends on S-040 (intent API) and S-042 (deployment strategies).
- Downstream consumers: U-006 (intent editing UI), N-020 (SuperNova deployment trigger, which can update an existing deployment instead of deleting and resubmitting).
- No new database columns are needed: the spec columns already exist, and `updated_at` plus the reset of `status.strategy_progress` are enough for the reconciler to notice a change. Adding a generation counter is a larger change and is not required for the behaviour above.
- Scale-to-zero already has meaning (`replicas: 0` stops all replicas but keeps the intent), so an update may legitimately set it. Do not conflate it with deletion.
