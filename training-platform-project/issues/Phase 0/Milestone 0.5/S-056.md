# S-056: Progress-aware resolver timeouts (replace the total pull bound)

## Description

Follow-up to S-055. The model resolvers wrap their downloads in
`aiohttp.ClientTimeout(total=settings.model_pull_timeout_s)`
(`app/model_resolvers/repo.py`, `app/model_resolvers/huggingface.py`). A
`total` bound measures wall-clock time for the whole transfer, so it cannot
tell a healthy slow download from a stalled one: a large model on a modest
link is cancelled at 30 minutes even though every byte was arriving on
schedule. Raising `model_pull_timeout_s` trades one arbitrary cutoff for a
larger one and lengthens the time a genuinely wedged transfer holds the
slot.

S-055 makes the resulting failure `recoverable` so the next round retries
and the operator sees an amber notice, but the transfer still restarts
from the beginning at every bound.

## Why the original prescription does not work

This issue previously asked for the `total` bound to be **replaced with a
read-idle bound** (`sock_read`), so that the timeout would measure silence
rather than duration. That cannot work on this hop, and implementing it as
written would make cold starts strictly worse.

The timeout in question guards control's `POST /models/pull` call to the
host — not the host's download from Harbor or the Hub. That route is
synchronous: *"The caller blocks until the model is fully available"*
(`solar_host/routes/models.py`, the `pull_model` docstring). Control
receives no bytes at all until the host has finished pulling, verifying and
writing its manifest, so from the socket's point of view a perfectly
healthy multi-GB download is indistinguishable from a dead peer. A
`sock_read` bound would fire on every download longer than the idle window,
which is a far tighter cutoff than the 30-minute `total` it replaced.

Read-idle bounds are the right tool one layer down, inside the host, where
bytes actually flow — but that is the host's own download code, not the
resolvers.

## Goal

The 30-minute inner bound stays for now. What this issue still wants is for
a pull that is demonstrably progressing not to be cut off by a clock, which
needs one of:

- **Align the inner bound with the outer one.** The reconciler's cold-start
  wait is bounded by `_action_timeout_s(action)`
  (`model_pull_timeout_s + host_start_timeout_s + _ACTION_TIMEOUT_S`) and is
  progress-aware, but the resolver's `total=model_pull_timeout_s` always
  fires first, so the outer judgement never gets to apply. Deriving the
  resolver bound from the same budget — or dropping it and letting the
  progress-aware wait be the only bound — makes the layer that *can* tell
  "working" from "wedged" the one that decides.
- **Make the pull non-blocking.** If `POST /models/pull` accepted the
  request and returned immediately, control would follow the pull through
  the `pull_progress` stream it already consumes, and no HTTP hop would need
  to stay open for the length of a download. Both `total` and `sock_read`
  become irrelevant, and the only bound left is the progress-aware one. This
  is the larger change and touches the host API.

Whichever is chosen, re-check `model_pull_timeout_s`'s documented meaning in
`docs/DEVELOPMENT.md` (the "belső korlát" paragraph) once the semantics
change. It is accurate as long as the bound remains a total-time one.

## Additional Notes

The resolvers are shared with paths outside the change that raised this,
which is why it was split out of S-055 rather than done there.

S-055's closing note describes the follow-up as "progress-aware `sock_read`
timeouts in the resolvers"; that description is superseded by the finding
above and is left in place only as a record of what was believed at the
time.

Interaction to preserve: the reconciler's progress-aware wait and the
`pull_progress` freshness check already distinguish "working" from
"wedged" at the control layer. The fix should make the resolver agree with
that judgement instead of pre-empting it.
