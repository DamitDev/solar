# S-034: Implement resource reservation API on solar-host

## Description

Solar Host reports local resource availability, but it does not yet have a way to reserve capacity for work that has been assigned but has not started. Solar Control needs this primitive before it can safely coordinate training jobs, migrations, and deployment reconciliation without overcommitting a host.

This issue adds host-local reservation primitives. Solar Host owns only the local accounting and execution checks; Solar Control remains responsible for placement decisions, migration decisions, and cluster-level coordination.

## Goal

- Implement `POST /resources/reserve` on solar-host. Request body should include requested VRAM/RAM, optional disk, workload type, requester/job identifier, and an optional TTL or expiration timestamp.
- Implement `DELETE /resources/reserve/{id}` to release a reservation explicitly. A running job's reservation must only be releasable when the job finishes or is cancelled — not during execution.
- Track active reservations in host-local state. Each reservation persists until the job completes. For running jobs, collect actual memory usage from the container runtime (Docker SDK `container.stats()`) so the system can distinguish real consumption from the reserved ceiling.
- Compute available resources for new work as `available = total - Σeffective`. For each reservation: `effective = requested` while pending, `effective = max(actual_usage, requested)` while running. This ensures a running job's reserved ceiling (the capacity it was promised) continues to block overcommitment, but real consumption is never double-counted against the reservation — the system reports whichever is larger per job.
- Include reservation details, per-job actual usage (when available), and the resulting effective availability in the host resource response and health/status payloads consumed by Solar Control.
- Reject reservations that would exceed available capacity with a clear 409 or 422 response.
- Add cleanup for expired reservations on non-running jobs so abandoned scheduling attempts do not permanently reduce capacity.
