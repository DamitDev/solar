# S-053: Drift circuit-breaker persistence and the status-hydration pin

## Description

S-049 added a churn circuit breaker that gives up after
`max_drift_replace_attempts` consecutive drift-driven REPLACE rounds and
records `BackendDriftUnsettled` instead of looping forever. The counter
was written into `status_json` and read back off the intent model, but
`_row_to_response` never hydrated it, so Pydantic supplied the field
default on every load.

The reconciler holds no cross-tick state of its own, so this made the
breaker unreachable: every tick started from zero, the counter never got
past one, and an unsettleable drift vector kept the intent in an endless
stop/recreate loop — exactly the failure S-049 existed to prevent. The
same gap affected `drift_unsettled_keys` (the breaker's message named no
keys) and `shortfall_reason` (the Degraded cause was dropped on read).

The existing breaker test passed against the broken code because it
assigned the counter directly instead of round-tripping it through the
database read path.

## Goal

- Hydrate `drift_replace_attempts`, `drift_unsettled_keys` and
  `shortfall_reason` in `_row_to_response` alongside the neighbouring
  `status.get` calls.
- Rewrite `tests/test_drift_circuit_breaker.py` so each simulated tick
  round-trips the persisted `status_json` back through `_row_to_response`
  rather than assigning the counter, and add a case proving the breaker
  actually trips at the threshold across reloads.
- Add a pin test asserting that **every** key `_update_status` writes into
  `status_json` is hydrated on read, so the next status field added to the
  write path cannot silently fail to survive a reload.
- Document in the spec (§8.2.2) that persistence and hydration are both
  load-bearing and must be added together.

## Additional Notes

Unit coverage: `tests/test_drift_circuit_breaker.py` and the hydration pin
in `tests/test_intents.py`. The pin is the durable half — it fails for any
future field, not just these three.
