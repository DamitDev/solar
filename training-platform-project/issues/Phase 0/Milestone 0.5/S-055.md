# S-055: Recoverable cold-start failures on the inner pull bound

## Description

S-051 made the reconciler's cold-start wait progress-aware: while the host
keeps reporting pull progress the outer wait extends, and a cold start
that is interrupted while the host was demonstrably working is marked
`recoverable` so the webui shows an amber "still working" notice instead
of a red failure.

An inner bound fires first and bypasses that. `resolve()` runs inside the
action itself and carries an `aiohttp.ClientTimeout(total=...)` of
`model_pull_timeout_s` (1800 s). Because it raises from inside the action
rather than from the progress-aware wrapper, the wrapper returns the
exception verbatim and `recoverable` is never set. A large model on a slow
link therefore fails hard at 30 minutes and is presented as a red error,
with nothing in the message distinguishing it from a genuine failure.

## Goal

- In the `except` block that builds `last_error`, treat a timeout raised
  from inside the action (`asyncio.TimeoutError`,
  `aiohttp.ServerTimeoutError`) as `recoverable = True` when Redis pull
  progress for `(host_id, model_source)` is fresher than
  `pull_progress_stale_after_s`, reusing the freshness check the
  progress-aware wait already performs. A wedged pull with stale progress
  stays a hard failure.
- Note the inner bound and the operator-facing meaning of `recoverable` in
  `docs/DEVELOPMENT.md`.

## Additional Notes

Unit coverage: `tests/test_action_timeouts.py` — a timeout raised from
inside the action with fresh progress yields `last_error.recoverable is
True`, a wedged pull does not, and a non-timeout failure never does.

This is the cheap half. The deeper fix — progress-aware `sock_read`
timeouts in the resolvers, so a downloading transfer is never cut off by a
total-time bound — is tracked separately in S-056; it touches a resolver
shared with paths outside this change's scope.
