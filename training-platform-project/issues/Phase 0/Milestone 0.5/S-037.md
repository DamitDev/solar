# S-037: Implement instance migration in solar-control

## Description

Solar Control needs to move inference instances between hosts so it can free resources for training, rebalance deployments, and satisfy declarative intents. Migration is a Solar Control responsibility because it requires cluster-level knowledge of hosts, model availability, priorities, and placement constraints.

Migration should recreate the instance on the target host from the original instance configuration. Model availability must be established by pulling from the authoritative model source through the existing distribution/pull flow, not by copying model files directly from one host to another.

## Goal

- Implement a Solar Control migration operation for moving an instance from a source host to a target host.
- Capture or load the complete instance configuration needed to recreate the instance on the target host, including model source, alias, runtime settings, and priority.
- Before creating the target instance, ensure the target host has the model by using S-019 model distribution and the existing Solar Host `POST /models/pull` flow.
- Stop the source instance and create the target instance in an order that is explicit and documented for the initial implementation.
- Enforce one replica per host for the same deployed model/alias before creating the target instance.
- Reject migration if the target host lacks required roles/resources or would violate placement constraints.
- Surface migration status and errors clearly to callers and logs.
- Include safeguards so `production` instances are not migrated casually by future automated flows without an explicit policy decision.

## Additional Notes

- Repo: `solar-control` at `/mnt/nvme/AI/damit-aiops/solar/apps/solar-control`
- Key files likely: instance management routes/services, host client/proxy code, model distribution routes/services from S-019, database models for instance config.
- Depends on S-019 (model distribution) and S-036 (instance priority levels).
- Downstream consumers: S-038 (reservation coordinator), S-041 (intent reconciliation), S-042 (rolling deployment strategy).
- Active training jobs from S-032/S-033 should be treated as non-migratable workloads. If migration is requested to free resources on a host running active training, the operation should account for that job usage and avoid interrupting it unless a later explicit cancellation/eviction policy is introduced.
- Solar Control owns migration orchestration. SuperNova should request resources or submit intents through Solar Control, not call Solar Hosts to move instances.
