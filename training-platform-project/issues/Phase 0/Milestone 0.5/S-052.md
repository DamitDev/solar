# S-052: Intent validation layer (vocabulary, field ownership, device contract, fleet checks)

## Description

Intent validation was mostly shape-level: any backend type accepted any
field, `device` was silently dropped for llama.cpp, `gpu_type` accepted
arbitrary tokens, and nothing checked the intent against the live fleet.
Impossible configurations were stored and only failed later at the host,
with no field-level error to guide the user. The reported symptom: an
intent with `device: mps` and `placement.gpu_type: nvidia_cuda` was saved,
then the host-side validation dropped the request.

## Goal

- Accelerator vocabulary: `VALID_GPU_TYPES` with aliases
  (`mps` -> `apple_mps`, `cuda`/`NVIDIA`/`NVIDIA-CUDA` -> `nvidia_cuda`,
  `rocm` -> `amd_rocm`), normalized at the API boundary.
- Field-ownership table: per-backend-type allowed fields; a field with the
  wrong backend type is a 422 with a field-level error instead of a silent
  host-side drop. `mmproj` is only valid for llm backends; `pooling` is
  advisory.
- Device contract: `device` is a HuggingFace-only field; a device/gpu_type
  contradiction (e.g. `apple_mps` vs `nvidia_cuda`) is a 422.
- Fleet-aware layer (`app/services/intent_validation.py`): unknown
  `host_allow`/`host_deny` ids and device-vs-allow-list contradictions are
  hard errors; replicas above eligible hosts, VRAM/RAM beyond the largest
  eligible capacity, all hosts draining, and unreported gpu_type are
  advisory warnings. Warnings never block an edit. The fleet checks reuse
  the real placement filter chain (`filter_durable_hosts`).
- `status.shortfall_reason` gives the Degraded message a specific cause.

## Additional Notes

Unit coverage: `tests/test_intent_validation_fleet.py` (9 tests),
`tests/test_shortfall_reason.py` (7 tests) and the C3 section of
`tests/test_intents.py`; integration coverage in
