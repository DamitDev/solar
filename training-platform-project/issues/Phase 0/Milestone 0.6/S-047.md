# S-047: Add an artifact upload relay to Solar Control

## Description

Some models we train cannot be published to HuggingFace, and there is currently no way to get a locally held model or dataset into the platform. The Data Repository is metadata-only and never proxies blobs; the only ingestion path is a SuperNova training pipeline whose final `upload_model` step pushes to Harbor from the job workspace.

A browser cannot push to Harbor directly: Harbor does not support CORS. Verified against the live registry — no `Access-Control-Allow-Origin` on any response, and `OPTIONS /v2/...` is rejected as "un-recognized request". Harbor is not deployed from `aiops-k8s`, so enabling CORS is not a change we control. The bytes must pass through a service we own.

Relaying is cheap because the OCI blob upload protocol is chunked. Solar Control can read the request body in fixed-size chunks and forward each one to Harbor, computing the sha256 as the bytes pass through, never holding more than one chunk. **No staging to disk and no PVC is needed**, which is what makes this fit inside the current pod limits — the cluster has no object storage and no ReadWriteMany volume for the solar stack.

Solar Control is the right home because the WebUI already talks only to Solar Control (the topology constraint from U-002), and because it already has Redis for cross-replica state.

## Goal

- Add five management endpoints under `/api/uploads` (session create, per-file stream, status, complete, abort) as specified in [docs/specs/artifact-upload.md](../../../docs/specs/artifact-upload.md) §4.2. They sit behind the existing management API key middleware.
- Stream each file to Harbor with the OCI chunked blob upload protocol: `POST` to open a session, `PATCH` per 8 MiB chunk with `Content-Range`, `PUT` with the digest computed while streaming. Read the request with `Request.stream()`; never call `await request.body()`.
- Store upload sessions in Redis (`app/redis_state/`) with a TTL so either replica can serve any request in a session.
- Validate up front, before any bytes move: category, artifact name against `^[a-z0-9][a-z0-9._-]{0,254}$`, version against `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$` and not the reserved `latest`, non-empty file list, and every file path relative with no `..` segments and no duplicates.
- Pre-flight the version conflict against the Data Repository so an operator fails in the form rather than after a long upload. Resolve the next `v{n}` when the version is omitted and return it.
- On completion, assemble the flat file-per-layer manifest (spec §2.1), push it, then register the version with an explicit `size_bytes` equal to the sum of file sizes. The Data Repository's fallback derives size from the manifest HEAD `Content-Length`, which is the size of the manifest JSON, not of the artifact.
- On registration failure, delete the just-pushed Harbor tag so a retry is not blocked by a half-created version.
- Add `HARBOR_URL`, `HARBOR_USERNAME`, `HARBOR_PASSWORD` settings. Solar Control holds no Harbor credentials today.
- Encode the four verified registry behaviours as tests (see Additional Notes) — each was an observed failure against real Harbor.
- Extend the integration stub Harbor with the OCI write path, including the CSRF-cookie and `_state` traps, and add end-to-end tests that finish with a Solar Host pull of the uploaded artifact.
- Update `aiops-k8s`: ingress body-size and request-buffering on both solar-control and solar-webui, the new secret and config keys, and raised CPU limits.
- Run `make test-solar-control`, `make lint-solar-control`, and `make integration`.

## Additional Notes

- Repo: `solar-control` at `/mnt/nvme/AI/damit-aiops/solar/apps/solar-control`, plus `aiops-k8s` at `/mnt/nvme/AI/damit-aiops/aiops-k8s`
- New modules follow existing conventions: `app/routes/management/uploads.py`, `app/services/uploads.py`, `app/models/uploads.py`, `app/redis_state/uploads.py`, `app/harbor/oci_push.py`
- Plan: [docs/plans/artifact-upload-implementation.md](../../../docs/plans/artifact-upload-implementation.md) §3
- **Four registry behaviours that are binding**, each verified against `imgrepo.damit.hu`:
  1. Harbor sets a `sid` cookie on `/v2/` responses; replaying it fails with `403 FORBIDDEN — CSRF token invalid`. The HTTP client must not persist cookies.
  2. The upload `Location` carries a `_state` query parameter that must be returned verbatim. Replacing the query string (e.g. `httpx` `params=`) fails with `404 BLOB_UPLOAD_INVALID`. Append `&digest=` instead.
  3. 8 MiB chunks are above the 5 MiB minimum that object-storage registry drivers impose, so the chunk size is safe regardless of Harbor's storage backend.
  4. A freshly minted bearer token is accepted mid-session, including on the closing `PUT`. Refreshing near the 30-minute TTL removes any ceiling on upload duration.
- **Topology constraint:** the WebUI must not call the Data Repository or Harbor directly. Everything goes through Solar Control.
- The `aiops-k8s` change must be applied to the cluster *before* the Solar Control image carrying the relay is rolled out, otherwise the first upload dies at the current 10 MB ingress cap. `proxy-request-buffering: "off"` is as important as the size cap: without it the ingress controller buffers the whole body to its own local disk.
- Depends on S-045 for the shared layout contract. U-007 is the WebUI consumer.
- Manual validation must use `test-` prefixed repositories in the `supernova` Harbor project, deleted afterwards.
