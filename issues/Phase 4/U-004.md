# U-004: Implement resource utilization dashboard in Solar WebUI

## Description

Solar WebUI shows resource information only per host card: a memory usage bar (`used / total` with a percentage) and a disk usage bar in `HostCard.tsx`, fed by `GET /api/hosts` and the `host_health` Socket.IO event. That answers "how full is this host?" but not "what is consuming it?" — inference instances, training job steps, and pending reservations are all invisible in the bar, and there is no cluster-wide view.

Once SuperNova starts scheduling training jobs, this matters operationally: an operator needs to know why a host has no free VRAM, whether the consumer is displaceable, and where a new workload could fit. S-035 provides the data with `GET /api/resources` — a per-host aggregate of roles, GPU type, total resources, running workload usage (inference instances *and* active job steps), reservations, and available resources, using the shared semantics `available = total - Σeffective` (per S-034: `effective = max(actual, requested)` for a running job, `effective = requested` for a pending reservation).

This issue adds the Solar WebUI dashboard that visualizes that breakdown per host and across the cluster.

## Goal

- Add a new `Resources` route and page (e.g. `/resources`), registered in the router and top navigation alongside the existing pages.
- Add a typed API client method for `GET /api/resources` in `src/api/client.ts`, plus resource aggregate types in `src/api/types.ts` (per-host entry with roles, GPU type, totals, workload usage, reservations, available).
- Render a per-host allocation breakdown that separates the consumers rather than showing one opaque used/total bar:
  - inference instance usage,
  - active training job step usage,
  - reserved-but-not-yet-running (pending reservations),
  - free/available.
  A segmented/stacked bar per resource (VRAM/RAM, plus disk where reported) is the intended presentation.
- Use the `available = total - Σeffective` value from the API as the source of truth. Do not recompute availability client-side with different arithmetic — the WebUI must agree with what the scheduler sees.
- Show per-host context that explains placement decisions: host `roles`, `gpu_type`, online/offline status, and the workload list behind each segment (instance aliases, job IDs, reservation owners) via tooltip, expandable panel, or detail table.
- Add a cluster-level summary: totals and free capacity across hosts, aggregated by role (e.g. training-capable free VRAM) and by GPU type, so "can we fit a 20 GB training job?" is answerable at a glance.
- Support the S-035 filters (`role=training`, `gpu_type=nvidia_cuda`, availability thresholds) as UI controls where the API exposes them.
- Handle unreachable/stale hosts the way S-035 does: mark them unavailable/stale and exclude them from free-capacity totals instead of silently counting or dropping them.
- Keep the view current: refresh on the existing `host_status`, `host_health`, and `instances_update` Socket.IO events (already handled in `useEventStream.ts` / `EventStreamContext.tsx`) plus a periodic refetch and a manual refresh button, matching the pattern used by the other dashboards.
- Follow existing UI conventions: Nord theme classes, `lucide-react` icons, `cn()`, and the existing color/formatting helpers in `src/lib/utils.ts` (`getMemoryColor`, `formatMemoryUsage`, `formatDiskUsage`) so thresholds look consistent with host cards.
- Run `npm run lint` (ESLint + Prettier) and verify the page against a running Solar Control with at least one host reporting reservations and/or an active job step.

## Additional Notes

- Repo: `solar-webui` at `/mnt/nvme/AI/solar/solar-webui`
- Key files: `src/App.tsx` (router + `Navigation`), `src/api/client.ts`, `src/api/types.ts`, `src/components/HostCard.tsx` (existing memory/disk bar pattern to extend or mirror), `src/components/GatewayDashboard.tsx` (dashboard page pattern: filters, refresh, live toggle), `src/hooks/useEventStream.ts` / `src/context/EventStreamContext.tsx` (host health/status events), `src/lib/utils.ts`.
- API: `GET /api/resources` from solar-control (S-035), reached through the existing `/api/control` proxy which injects the management API key. No new proxy target or credential needed.
- Depends on S-035 (aggregated resource query API). Data quality depends transitively on S-034 (host reservation primitives, `effective` semantics), S-003/S-004 (disk and available memory reporting), S-006 (role/resource fields on hosts), and S-033 (active job step awareness in host status).
- Resource semantics reference: S-034/S-035 define `available = total - Σeffective`; `docs/specs/deployment-intent.md` Sections 4.6 and 8.4 describe how placement consumes the same values. Keep the dashboard's vocabulary aligned with both so operators see the same numbers the placement policy uses.
- **Charting:** the repo has no charting library (`package.json` has `reactflow` for the routing graph only). Build the bars with Tailwind/SVG in the style of the existing memory/disk bars. Adding a charting dependency is a decision for the supervisor — ask before introducing one.
- Related: U-001 (training activity indicators on host views) covers the same training-awareness data from S-033 — coordinate so the two issues share types/components instead of each building their own job-step rendering. U-003 benefits from this view when choosing placement constraints for an intent.
- **Topology constraint:** the WebUI reads resources from Solar Control only, never from Solar Host endpoints directly.
