# U-003: Implement declarative intent submission UI in Solar WebUI

## Description

Solar WebUI manages inference **imperatively**: the operator picks a host card, opens `AddInstanceModal`, fills a full backend config (model path, alias, backend params), and Solar Control proxies that to the chosen Solar Host. The operator chooses *where* the model runs.

S-039 specified, and S-040 implements, the declarative alternative: the client submits a desired state — served alias, model source URI, replica count, priority, strategy, placement constraints — to `POST /api/intents`, and Solar Control decides placement and reconciles the cluster toward that state. This is README Decision #12: Solar WebUI shifts from "configure instance X on host Y" to "submit intent, monitor how Solar Control arranges".

This issue builds the Solar WebUI side of that contract: an intent submission form, an intent list, and a per-intent status view. The [Declarative Deployment Intent API Specification](../../docs/specs/deployment-intent.md) is the source of truth for every field, phase, and status value used here — Section 4 for the form, Sections 10.1–10.4 for the status view.

Two constraints shape the scope:

- **S-040 stores intents but does not reconcile them.** Reconciliation lands in S-041 and strategies in S-042. Until then intents report `status.phase = "pending"` and `status.reconcile = "idle"` (spec Section 7.3). The UI must make "stored" visibly distinct from "running" so operators are not misled into thinking a deployment happened.
- **S-040 has no update endpoint.** Create / list / get / delete only (spec Section 12.5). The UI must not present an edit or scale control that cannot be honored.

## Goal

### Intent submission form

- Add a new `Intents` route and page (e.g. `/intents`), registered in the router and top navigation.
- Add typed API client methods for `POST /api/intents`, `GET /api/intents`, `GET /api/intents/{id}`, and `DELETE /api/intents/{id}` in `src/api/client.ts`, with intent request/response/status types in `src/api/types.ts` mirroring spec Sections 4 and 10.
- Build the intent form with the spec Section 4.1 fields:
  - `alias` (required) — served model name / deployment identity.
  - `model_source` (required) — model source URI; accept `repo://`, `huggingface://`, `local://` per [model-source-uri.md](../../docs/specs/model-source-uri.md).
  - `replicas` (default `1`, `>= 0`) — note in the UI that one replica means one host (one-replica-per-host rule).
  - `priority` — `production` | `staging` | `ephemeral`, default `production`, with a short explanation of displacement behavior (spec Section 4.3).
  - `strategy` — `rolling` | `immediate`, default `rolling`, with the trade-off stated (`immediate` causes a serving gap).
  - `backend` (required) — backend type plus runtime params. Reuse the backend/mode selection and per-backend field logic already implemented in `AddInstanceModal.tsx` rather than duplicating it.
  - `placement` (optional) — `roles` (default `["inference"]`), `gpu_type`, `host_allow`, `host_deny`. Populate host pickers and `gpu_type` options from live host data (`GET /api/hosts` / `host_status` events).
  - `resources` (optional) — `vram_gb`, `ram_gb`.
  - `metadata` (optional) — free-form key/value labels.
- Enforce the client-side shape rules from spec Sections 4.7 and 6: `backend` must **not** contain `alias`, `model_source`, `host`, `port`, or `api_key`; validate URI scheme, `replicas >= 0`, and the `priority`/`strategy` enums before submitting. Server validation stays authoritative.
- Surface server errors meaningfully: `409 Conflict` (an active intent already claims the alias) and `400`/`422` validation errors including the structured `errors[]` list from spec Section 12.6.

### Intent list and status view

- List active intents with `alias`, `model_source`, `replicas`, `priority`, `strategy`, `status.phase`, `status.ready_replicas` / `desired_replicas`, and timestamps — no per-item fetch required (spec Section 12.2).
- Render the lifecycle `phase` as a distinct badge for each of `pending`, `reconciling`, `ready`, `degraded`, `failed`, `deleting`, `deleted` (spec Section 7.2), plus `status.reconcile`.
- Show a per-intent detail view with: replica counts (`desired` / `observed` / `ready` / `updated`), `available`, `shortfall`, the `replica_set` table (host, instance, state, model source, healthy, message, updated_at), `conditions` (`Available`, `Progressing`, `Conflict`, `Degraded`), `strategy_progress` when in flight, and `last_error`.
- Make partial fulfillment readable as a stable state, not an error: `degraded` with a non-zero `shortfall` means "serving with fewer replicas than requested" (spec Section 8.6).
- Implement intent deletion with a confirmation that states the consequence (managed instances are stopped and the alias leaves the gateway registry). Expose the `?orphan=true` option from spec Section 12.4 only if the supervisor wants it in v1.
- Do not offer edit/scale controls while only create/list/get/delete exist. If the operator needs to change a deployment, the UI should explain that an update endpoint is pending (spec Section 12.5) rather than silently doing delete-then-create, which causes downtime for `production`.

### Coexistence with imperative instance management

- Keep the existing per-host `AddInstanceModal` flow working. Intents **supplement** it in this phase: manual instances remain valid and are never touched by reconciliation (spec Section 5.1). See the decision note below.
- Show ownership on instances: when an instance config carries `managed_by = "intent"` / `intent_id`, badge it as intent-managed in `InstanceCard` / `HostCard` / `UnifiedTable`, and link to the owning intent.
- Warn before manual stop/delete of an intent-managed instance, since the reconciler will recreate it.
- Where a manual instance occupies an alias a reconciler wants (the `Conflict` condition, spec Section 5.3), present the conflict clearly so the operator can resolve it.

### Live updates

- Consume the `intent_update` and `intent_removed` Socket.IO events on the existing `/webui` namespace (spec Section 10.4) through the existing `useEventStream` / `EventStreamContext` plumbing.
- Because those events ship with S-041, implement a polling fallback on `GET /api/intents` / `GET /api/intents/{id}` so the page is useful against an S-040-only backend.

### General

- Follow existing UI conventions: Nord theme classes, `lucide-react` icons, `cn()` helper, and the loading/error/empty-state patterns already used in `Dashboard.tsx` and `GatewayDashboard.tsx`.
- Run `npm run lint` (ESLint + Prettier) and verify the flows against a running Solar Control.

## Additional Notes

- Repo: `solar-webui` at `/mnt/nvme/AI/solar/solar-webui`
- Key files: `src/App.tsx` (router + `Navigation`), `src/api/client.ts`, `src/api/types.ts`, `src/components/AddInstanceModal.tsx` (backend field logic to reuse), `src/components/InstanceCard.tsx` / `HostCard.tsx` / `UnifiedTable.tsx` (ownership badges), `src/hooks/useEventStream.ts` and `src/context/EventStreamContext.tsx` (Socket.IO events), new intent page/form/detail components.
- **Reference (authoritative): `docs/specs/deployment-intent.md`** — Section 4 (request schema, priorities, strategies, placement, resources, validation), Section 5 (`managed_by` / `intent_id` ownership), Section 7 (lifecycle phases and the S-040-only `pending` behavior), Sections 10.1–10.3 (status object, field reference, conditions), Section 10.4 (`intent_update` / `intent_removed` events), Section 11.4 (`strategy_progress`), Section 12 (API shapes and error model), Section 13 (worked examples for the flows the UI must render).
- Depends on S-040 (intent submission/list/get/delete API). Practical dependencies for a fully meaningful view: S-041 (reconciliation — intents actually materialize), S-042 (`strategy_progress` populated), S-036 + the spec Section 5.1 instance-config change (`priority`, `managed_by`, `intent_id` round-tripped through solar-host/solar-control so ownership badges work).
- API access: all `/api/intents` calls go through the existing `/api/control` proxy, which injects the management API key. No new auth surface (spec Section 14).
- **Topology constraint:** the WebUI submits intents to Solar Control only and never translates an intent into a direct Solar Host call (spec Sections 1.3 and 14).
- Related: U-002 (model catalog) is the intended entry point for "deploy this model" and should pre-fill `alias` and `model_source` into this form. N-019/N-020 are the SuperNova-side clients of the same intent contract — keep field naming identical so both clients stay consistent.
- **Decision point for the supervisor:** the roadmap wording is "replace *or* supplement per-host instance creation". This issue is written as *supplement* (both paths available, intents becoming the primary deployment path) because S-040 alone cannot reconcile, so removing the imperative flow would leave operators unable to deploy. Confirm before implementing; if "replace" is preferred, it should land after S-041/S-042 as a separate follow-up.
