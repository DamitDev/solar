# S-035: Implement aggregated resource query API on solar-control

## Description

Solar Control needs a cluster-wide view of host resources before it can place training jobs, coordinate reservations, or drive declarative deployment reconciliation. Individual hosts expose local resource data, but callers should not need to fan out to Solar Hosts directly.

This issue adds a Solar Control API that aggregates host capacity, running workloads, and reservations. Solar Control owns the cluster-level resource view and is the only resource API SuperNova should call.

## Goal

- Implement `GET /api/resources` in solar-control.
- Return each known host with roles, GPU type, total resources, running workload usage, reserved resources, and available resources.
- Use the resource semantics `available = total - running - reserved` consistently for VRAM/RAM and any other reservable resource included in the response.
- Include running inference instances and active job steps in the workload summary when that data is available.
- Include reservation details or reservation totals from solar-host without exposing host-only implementation details unnecessarily.
- Support useful filters such as `role=training`, `gpu_type=nvidia_cuda`, and availability thresholds if they fit existing API patterns.
- Handle unreachable hosts gracefully by marking them unavailable/stale instead of failing the entire aggregate request.
- Require the existing Solar Control management/API-key authentication.

- Repo: `solar-control` at `/mnt/nvme/AI/solar/solar-control`
