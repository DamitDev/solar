# S-034: Implement resource reservation API on solar-host

## Description

Solar Host reports local resource availability, but it does not yet have a way to reserve capacity for work that has been assigned but has not started. Solar Control needs this primitive before it can safely coordinate training jobs, migrations, and deployment reconciliation without overcommitting a host.

This issue adds host-local reservation primitives. Solar Host owns only the local accounting and execution checks; Solar Control remains responsible for placement decisions, migration decisions, and cluster-level coordination.

## Goal

- Implement `POST /resources/reserve` on solar-host. Request body should include requested VRAM/RAM, optional disk, workload type, requester/job identifier, and an optional TTL or expiration timestamp.
- Implement `DELETE /resources/reserve/{id}` to release a reservation explicitly.
- Track active reservations in host-local state so available resources for new work are computed as `total - running - reserved`.
- Include reservation totals and effective availability in the host resource response and health/status payloads consumed by Solar Control.
- Reject reservations that would exceed available capacity with a clear 409 or 422 response.
- Ensure reservations are not confused with running workloads: once a reserved job starts, the reservation should either be converted into running usage or released as part of the start flow.
- Add cleanup for expired reservations so abandoned scheduling attempts do not permanently reduce capacity.
