# S-040: Implement intent submission/list/delete API in solar-control

## Description

Once the declarative intent contract is specified, Solar Control needs API endpoints to store desired deployment state. This issue implements intent persistence and basic lifecycle APIs only. The API should validate and record intents, but actual instance creation, migration, and stop actions happen when the reconciliation engine is implemented in S-041.

## Goal

- Implement `POST /api/intents` in solar-control to submit desired deployment state following the S-039 specification.
- Implement `GET /api/intents` to list active intents with status, timestamps, alias, model source, replica count, priority, and strategy.
- Implement `GET /api/intents/{id}` if it fits existing API conventions.
- Implement `DELETE /api/intents/{id}` to remove an intent or mark it deleted, preparing reconciliation to scale down/remove managed instances later.
- Persist intents in Solar Control storage so they survive process restarts.
- Validate required fields, supported priorities (`production`, `staging`, `ephemeral`), supported strategies, replica count, model source URI format, and placement constraints.
- Return status that makes it clear whether the intent is only stored or has been reconciled.
- Require existing Solar Control management/API-key authentication.

## Additional Notes

- Repo: `solar-control` at `/mnt/nvme/AI/solar/solar-control`
- Key files likely: new intent route/service modules, database models/migrations, Pydantic request/response models, auth/router registration.
- Depends on S-039 (declarative intent API specification).
- Reference: `docs/specs/deployment-intent.md` — Section 4 (intent schema + validation), Section 12 (create/list/get/delete API shapes and error model), Section 7.3 (store-only `pending`/unreconciled status until S-041), Section 5 (the `managed_by`/`intent_id` ownership fields to round-trip through the instance config).
- Downstream consumers: S-041 (intent reconciliation), S-042 (deployment strategies), U-003 (Solar WebUI intent submission), N-020 (SuperNova deployment trigger).
- S-041 is needed before intents materialize into running/stopped instances. Until then, accepted intents should be stored and reported as pending or unreconciled rather than silently creating workloads.
- Keep intent APIs on Solar Control. SuperNova and WebUI should not translate intents into direct Solar Host calls.
